The problem isn't lack of data.
It's that the data is in three silos that don't pivot.
We have plenty of metrics. We have plenty of logs. We have traces (sometimes). They live in different systems. The traceId, when it exists, doesn't make it to the metric. The log line doesn't carry the spanId. So when something breaks, the operator does the pivot manually — by guessing timestamps and grep'ing across three tools. That's the problem OTel was designed to fix.

§1 What OpenTelemetry is

  • Vendor-neutral observability standard — CNCF graduated, second only to Kubernetes in commit volume.
  • Three deliverables that compose: API, SDK, Collector.
  • OTLP is the wire format — protobuf over gRPC or HTTP.
  • Spring Boot, Quarkus, .NET, Go, Python, Node, Ruby — all have official SDKs that converge on OTLP.
Instrument once. Decide who you pay later.
OTel is not a backend, not a UI, not a SaaS. It's an instrumentation standard plus a forwarding component (the Collector). The big idea: separate the act of producing telemetry from the act of storing it. You can change vendors — Datadog, New Relic, Honeycomb, Grafana Cloud, self-hosted LGTM — without changing a line of application code.

§1 The three signals

Metrics

Counters, gauges, histograms. Aggregate. Cheap to store. Great for "is the box on fire."

Logs

Structured records. Lossy at scale. Great for "what was the error message."

Traces

Causally-linked spans across processes. Great for "where did the time go."

Each useful alone. Transformative together — when they share a traceId.
Ten seconds per signal. Then the punchline: the value isn't additive — it's multiplicative. A metric without a trace tells you something's wrong; a trace without logs tells you which service; the three together tell you exactly what to fix. This is the entire reason for this talk.

§1 Why it matters

Before OTel

  • Vendor-specific agent per language
  • Re-instrument when switching tools
  • Each signal in its own format
  • Trace context rarely propagates

With OTel

  • One SDK per language, neutral
  • Swap backends without re-instrumenting
  • OTLP as a single wire format
  • W3C trace context in every span
The "instrument once, decide later" line is worth pausing on. Real-world impact: teams who instrumented with proprietary APMs in 2018 had to re-instrument when they switched vendors. Teams who instrumented with OTel in 2022 changed a single env var. That's the difference.

§2 Three approaches diagram 09

Auto

Bytecode-instrumenting agent. -javaagent:.... Zero code change.

Manual

Hand-written spans via the OTel API or Micrometer Observation.

Hybrid

Auto for the seams + manual for your domain. This is what production looks like.

Almost every Spring Boot deployment in the wild that I've seen is doing the hybrid model — they just may not have explicitly chosen it. The agent gets attached, then over time someone adds spans around hot business operations. That's fine. That's correct. We just need to be intentional about it.

§2 Auto-instrumentation, deep

java -javaagent:opentelemetry-javaagent.jar \
     -Dotel.service.name=order-service \
     -Dotel.exporter.otlp.endpoint=http://collector:4318 \
     -jar app.jar
  • ~120 instrumentations ship with the agent — HTTP servers/clients, JDBC, Kafka, Redis, gRPC, Lettuce, MongoDB.
  • Bytecode manipulation at startup (ByteBuddy). No source code changes, no recompile.
  • Configuration via env vars or system properties.
  • Costs: 5–10% startup time, 1–3% steady-state CPU. Occasional shaded-jar surprises.
Pull up the supported-libraries.md page in a tab if asked — it's a long list. Common pitfall: the agent doesn't see classes loaded by custom classloaders (some shaded fat-jars). Spring Boot is fine. Quarkus has its own native instrumentation path. .NET is similar. Go does NOT have an auto-agent — that's the major language gap.

§2 The Spring Boot 4.0.x reality

<dependency>
  <groupId>io.micrometer</groupId>
  <artifactId>micrometer-tracing-bridge-otel</artifactId>
</dependency>
<dependency>
  <groupId>io.opentelemetry</groupId>
  <artifactId>opentelemetry-exporter-otlp</artifactId>
</dependency>
  • Spring Boot 4.0 = Jakarta EE 11, Java 25 first-class, Jackson 3 default.
  • micrometer-tracing-bridge-otel is the recommended path. The Observation API spans land in OTLP.
  • Heads up: ZipkinSpanExporter is deprecated in 4.0, gone in 4.2. OTLP only.
Two-line dep change is what gives you basic auto-config: every HTTP request a server span, every RestClient call a client span, every JDBC statement (with the agent) a child span. Before this, you'd need Spring Cloud Sleuth + Zipkin shenanigans. Spring Boot 3+ killed Sleuth and rebased on Micrometer Observation. Spring Boot 4 doubles down on it.

§3 Pull vs push

Prometheus

  • Scrapes /metrics endpoints
  • Battle-tested at scale
  • PromQL is its own language
  • Single-zone friendly
  • Cardinality-bounded by design

OpenTelemetry

  • Apps push OTLP to a Collector
  • Multi-signal: metrics, logs, traces
  • Vendor-neutral semantic conventions
  • Exemplars first-class
  • Backend-agnostic
These are not opposing camps. Prom solves "I want to scrape my apps over HTTP and store time series." OTel solves "I want one wire format for everything I emit." Where they overlap is metrics — and they overlap intentionally.

§3 The bridge diagram 10

diagrams/10-otel-vs-prometheus.excalidraw Prometheus ←→ Collector ←→ OpenTelemetry scrape → OTLP, or remote_write → Prom; both are first-class
The Collector has receivers and exporters. A Prometheus receiver scrapes /metrics endpoints just like Prom does. A Prometheus remote_write exporter sends OTel metrics into a Prom-compatible store like Mimir. Both directions work. Most realistic deployments do both: scrape kube-state-metrics with the Prom receiver, push app metrics with OTLP from the SDK.

§3 When to use what

Use casePrometheusOpenTelemetry
Kubernetes infra metrics✓ scrape kube-state-metrics· receive via OTel scrape

AND, not OR. Most prod deployments run both.
Don't get caught in religious arguments. Prom isn't going anywhere — too much value in PromQL, alerting, the existing operational ecosystem. OTel is winning the application instrumentation layer, especially as more vendors converge on OTLP as their wire format.

§4 The LGTM stack diagram 11

diagrams/11-lgtm-architecture.excalidraw App → Collector → Tempo · Loki · Prom (Mimir) → Grafana all-in-one image: docker.io/grafana/otel-lgtm:0.8.1

§4 Podman compose, in practice

services:
  lgtm:
    image: docker.io/grafana/otel-lgtm:0.8.1
    ports: [ "3001:3000", "4317:4317", "4318:4318" ]
    volumes:
      - ./grafana/provisioning/datasources:/otel-lgtm/grafana/conf/provisioning/datasources:Z
    tmpfs: [ /tmp ]
    user: "0"
  service:
    build: { context: ./service, dockerfile: Containerfile }
    environment:
      OTEL_EXPORTER_OTLP_ENDPOINT: "http://lgtm:4318"
      OTEL_SERVICE_NAME: "demo01-service"
  • :Z on bind mounts — SELinux on Fedora/RHEL.
  • Fully-qualified image names (docker.io/...) — podman doesn't assume.
  • tmpfs + user: "0" sidesteps rootless-podman volume ownership pain.
These three lessons cost real time. The :Z is the single most common podman gotcha. The fully-qualified image name is the second. The volume ownership issue with rootless podman bites everyone once. Photograph this slide.

§5 How it actually works

App side

management:
  metrics:
    distribution:
      percentiles-histogram:
        http.server.requests: true
logging:
  pattern:
    correlation: "[%X{traceId:-},%X{spanId:-}]"

Grafana side

# datasources.yaml
- name: Loki
  jsonData:
    derivedFields:
      - name: TraceID
        datasourceUid: tempo
        matcherRegex: "\\[([a-f0-9]{32}),"
        url: "${__value.raw}"
Three lines of YAML each. That's the whole trick.
Histogram exemplars are the underused killer feature. Most teams have histograms but never enable exemplars, so the dot-click pivot doesn't work. One Spring Boot property turns it on. The Logback %X{traceId} pattern works because micrometer-tracing-bridge-otel installs the MDC mapping automatically. The Grafana derivedFields regex is what makes the traceId clickable in log lines.

Quick math: 1000 traces/second × 86400 seconds/day × 30 days × ~5KB/trace = ~13 TB. Multiply by the cost of your traces backend and you'll find observability is suddenly your second-largest cloud bill.

§6 Head vs tail diagram 13

diagrams/13-head-vs-tail-sampling.excalidraw Head: decide at span start. Tail: decide at trace end. Production answer: parentbased_traceidratio + Collector tail_sampling
Head sampling: cheap, predictable, blind to outcome. Tail sampling: smart (keep all errors, all slow traces, percentage of normal), buffers entire traces in the Collector before deciding. The Collector needs RAM proportional to your trace duration × your span rate. Most production: both. Head sampling at the app to throttle output, tail sampling at the gateway Collector to keep the interesting traces.

§8 Red Hat build of OpenTelemetry

  • Operator-managed via the OpenTelemetryCollector CRD.
  • Cluster-supported lifecycle — patches and CVEs without rolling your own.
  • Tested against OpenShift's networking, security, and SCC model.
  • UBI-based collector image; same support contract as the rest of your platform.
apiVersion: opentelemetry.io/v1beta1
kind: OpenTelemetryCollector
metadata: { name: gateway, namespace: observability }
spec:
  mode: deployment
  replicas: 3
  config: |
    receivers: { otlp: { protocols: { grpc: {}, http: {} } } }
    exporters: { otlphttp: { endpoint: http://tempo:4318 } }
The Red Hat build of OpenTelemetry is a tech-preview-graduating-to-GA productized version of upstream OTel components, packaged with an Operator. If you're on OpenShift, this is the path of least resistance: declarative Collector definitions, CR-driven config, automatic upgrades.

§8 Deployment patterns diagram 15

diagrams/15-openshift-collector-patterns.excalidraw Sidecar · DaemonSet · Deployment (gateway) most teams: DaemonSet → centralized Deployment gateway
Three patterns, three trade-offs. Sidecar = strongest isolation, highest overhead (one Collector per pod). DaemonSet = balanced, one per node, scales naturally. Deployment = centralized gateway, lets you do tail sampling, costs a network hop. Production at scale: DaemonSet for collection, Deployment for the gateway that does the smart routing and sampling.

§8 OpenShift gotchas

  • Service mesh emits proxy-level spans only. You still need app-level instrumentation.
  • Routes preserve traceparent by default — Ingresses sometimes don't (check your annotations).
  • Plan SCCs for the Collector — DaemonSet usually needs privileged for hostPath log scraping.
  • Network policies: Collector needs egress to your backend store (or to the gateway Collector).
  • Use the UBI-based Collector image, not contrib, if you want support.
These are the things that bite you on day-2. Especially the service-mesh-only spans — Istio, Linkerd, OpenShift Service Mesh all emit envoy/proxy spans, but those don't have your business context. You need both: mesh spans for routing visibility, app spans for "why did THIS request fail."

Five takeaways

  1. Three signals, one identifier — design for correlation from day one.
  2. Auto-instrument first; hand-instrument the seams.
  3. OTel and Prometheus compose. They don't compete.
  4. Sample at the head in dev, at the tail in prod.
  5. The Collector is the most important thing you'll deploy. Invest in it.

bonus The default GC nobody talks about

  • UBI9 OpenJDK images ship with Shenandoah as the default collector.
  • Every other major distro — Temurin, Corretto, Microsoft, Azul — defaults to G1GC.
  • If your image is FROM registry.access.redhat.com/ubi9/openjdk-21-runtime, you're already on it. No flag.
  • Spring Boot apps are heap-allocation heavy: bean wiring at startup, JSON serde + request scope at runtime. Shenandoah handles that profile beautifully.
Generational since JDK 21. Concurrent evacuation. ~5% memory overhead.
Most Spring Boot devs running on UBI9 don't realize they're getting a sub-10ms-pause GC for free. They think they have G1 because that's the OpenJDK default. They don't. The Red Hat distribution flips it. Project Shenandoah was started at Red Hat, the upstream maintainers are Red Hat employees — this isn't a fork, it's first-party investment.
